# Known failures for the SQLAlchemy dialect compliance suite (test/test_suite.py)
#
# Purpose: this manifest lets the official SQLAlchemy suite GATE CI (see #380,
# #463) while tolerating the documented set of currently-failing tests.
# conftest.py reads this file and applies a strict xfail to each node id listed
# for the CURRENT LANE: a listed test that FAILS is xfailed (tolerated), but a
# listed test that PASSES becomes an XPASS -> a hard failure, forcing the entry
# to be trimmed. Any NEW failure not listed for the lane fails CI.
#
# LANES. Every entry is keyed to the lanes it is known to fail in:
#
#   <node id>  <lane> [<lane> ...]
#
#   where <lane> = <driver>@sa<major.minor>, or
#                  <driver>@sa<major.minor>@cubrid<major.minor> for a failure
#                  that occurs on one CUBRID server version only. Only the
#                  (lane, server) pairs CI gates are accepted:
#                  cubrid@sa2.0@cubrid11.4, pycubrid@sa2.0@cubrid10.2 and
#                  pycubrid@sa2.1@cubrid11.4 (test/conftest.py).
#
#   cubrid@sa2.0     cubrid://          CUBRIDdb (cubrid-python v11.3.0.51),
#                                       SQLAlchemy 2.0.53, gated on CUBRID 11.4
#   pycubrid@sa2.0   cubrid+pycubrid:// pycubrid 1.7.1, SQLAlchemy 2.0.53,
#                                       gated on CUBRID 10.2
#   pycubrid@sa2.1   cubrid+pycubrid:// pycubrid 1.7.1, SQLAlchemy 2.1.1,
#                                       gated on CUBRID 11.4
#
# Every lane was captured on both CUBRID 10.2 and 11.4 (fresh databases).
#
# The driver comes from the --dburi dialect, the SQLAlchemy major.minor from
# the installed SQLAlchemy and the server version from the connection, so an
# entry only ever xfails in the lanes it names:
# a pycubrid-only failure cannot hide a CUBRIDdb regression and vice versa.
# There is no "all lanes" wildcard. A test that fails in several lanes lists
# each one, and strictness is per lane: when a test starts passing on one
# driver only, the XPASS in that lane forces removal of just that lane tag.
# An entry without a lane tag, or with an unknown one, is a load error.
#
# In a gating cell (CUBRID_STRICT_KNOWN_FAILURES=1), conftest.py also fails
# the run when the lane has no entries at all (no reviewed baseline, so a new
# driver or SQLAlchemy minor cannot silently gate on an empty list), when an
# entry for the lane matches no collected node (stale baseline), when a listed
# entry is SKIPPED instead of xfailed, or when the installed SQLAlchemy is not
# the release the lane was captured with. Each node id may appear only once.
#
# Node ids are version-agnostic w.r.t. the CUBRID server: the live suite
# parametrizes class names with a server-version suffix (e.g.
# ...Test_cubrid+pycubrid_11_4_6_1963); conftest.py strips that suffix before
# matching, so entries here use the bare class name.
#
# BASELINES ARE SQLALCHEMY- AND DRIVER-VERSION-SPECIFIC. SQLAlchemy changes
# suite parametrization between releases (e.g. the ObjectKind flag string
# ordering in ComponentReflectionTest.test_get_multi_columns changed between
# 2.0.36 and 2.0.53; 2.1 adds NameDenormalizeTest and fixes the HasTableTest
# view DDL), so each lane is a snapshot of the exact versions above, and the
# gating CI steps pin them. Bumping SQLAlchemy or the pinned pycubrid requires
# recapturing the affected lane: run the suite for that lane without
# CUBRID_STRICT_KNOWN_FAILURES, diff the failures, classify each one, and edit
# only that lane's tags. See docs/DEVELOPMENT.md ("SQLAlchemy compliance
# lanes").
#
# Each group links to the follow-up issue that tracks the real fix. Removing an
# entry (fixing the bug) is the goal; adding one requires a linked reason.
#
# CLASSIFICATION (every group is exactly one of these — see the [CATEGORY] tag):
#   [DIALECT BUG]          sqlalchemy-cubrid must fix this. Actively tracked.
#   [DRIVER LIMITATION]    CUBRIDdb or pycubrid behaves differently below the
#                          dialect; cannot be fixed in the dialect (the other
#                          driver often passes). Documented, driver-qualified.
#   [BACKEND / SUITE LIMIT] CUBRID does not support the feature, or the
#                          SQLAlchemy compliance suite asserts backend-specific
#                          behavior a third-party dialect cannot satisfy. Stable
#                          by design; will not be "fixed" in the dialect.
# Tests that are not applicable to CUBRID at all are excluded in
# sqlalchemy_cubrid/requirements.py (with a reason) instead of listed here.
#
# RECAPTURED IN #463 after fixing requirements.py: every requirement property
# returned the same shared exclusions.open()/closed() object, and SQLAlchemy's
# stacked @requires decorators extend that object in place, so after
# collection every "open" requirement was effectively closed and large parts of
# the suite silently skipped. With fresh objects ~300 more tests run per lane;
# the entries below classify the failures that surfaced. The same change opened
# reflects_pk_names and implicitly_named_constraints (the suite reported
# unexpected successes) and gated unicode_ddl on a UTF-8 database.
#
# As of this baseline (entries per lane, CUBRID 11.4 / 10.2):
#   cubrid@sa2.0 77 / 70, pycubrid@sa2.0 (gated on 10.2 only) 63,
#   pycubrid@sa2.1 67 / 60;
# 0 XPASS, 0 unclassified. The 7 server-specific entries are
# BizarroCharacterTest::test_reflect_comments on 11.4. No compliance failure
# is attributable to the open pycubrid issues (cubrid-lab/pycubrid#390, #395,
# #430, #431) beyond the -924 exception class noted under CTETest; those are
# covered by targeted strict xfails elsewhere (#480-#482). Every [DIALECT BUG]
# group found by this recapture links its tracking issue (#529-#535); the
# #535 JSON as_numeric() group was removed when it was fixed.
